# anime-db-bot

`anime-db-bot` — Telegram-бот для поиска аниме и постепенного объединения информации из нескольких внешних баз данных в одной карточке.

Сейчас основной источник — **Shikimori GraphQL**. Архитектура проекта специально разделена на модули, чтобы каждый новый источник можно было добавлять, менять или полностью отключать независимо от остальных.

## Что уже умеет бот

- искать аниме по названию через Shikimori;
- сортировать результаты поиска по популярности;
- листать результаты поиска по страницам без общего лимита со стороны бота;
- показывать подробную карточку выбранного аниме;
- встраивать обложку прямо в rich message вместе с текстом;
- показывать основную информацию, названия, описание, команду и сэйю;
- открывать подробные разделы нажатием на текст внутри rich message;
- редактировать уже отправленную карточку вместо отправки большого количества новых сообщений;
- оставлять `← Назад` и `◀️ / ▶️` обычными inline-кнопками;
- автоматически разбивать очень длинные разделы на страницы;
- работать как через официальный `api.telegram.org`, так и через собственный `telegram-bot-api`;
- автоматически запускаться в отдельной tmux-сессии через `start.sh`.

### Почему источники вынесены отдельно

Каждая внешняя база должна жить в собственном файле внутри `sources/`.

Например:

```text
sources/
├── shikimori.py
├── anilist.py
├── anidb.py
├── animethemes.py
└── skipdb.py
```

Так код одного API не смешивается с другим. Если источник перестал работать или больше не нужен, его можно заменить или удалить без переписывания всей Telegram-логики.

## Текущий поток `/anime`

Пример:

```text
/anime slime
```

Бот:

1. отправляет поисковый запрос в Shikimori;
2. получает страницу результатов;
3. показывает найденные аниме inline-кнопками;
4. при необходимости позволяет переходить между страницами поиска через `◀️` и `▶️`;
5. после выбора получает полные данные конкретного аниме;
6. отправляет одну rich-карточку с обложкой и основной информацией;
7. подробные разделы открываются внутри этого же сообщения.

## Поиск без общего лимита

Раньше бот запрашивал только первые 5 совпадений.

Сейчас используется пагинация Shikimori:

```text
Страница 1
[аниме 1]
[аниме 2]
...
[аниме 10]
[ Стр. 1 ] [ ▶️ ]
```

После перехода:

```text
[ ◀️ ] [ Стр. 2 ] [ ▶️ ]
```

У бота больше нет собственного общего ограничения на количество доступных результатов. Он получает следующие страницы по мере необходимости.

Поисковые запросы временно сохраняются в памяти процесса, чтобы `callback_data` не приходилось заполнять длинным названием аниме. После перезапуска бота старые кнопки поиска могут устареть — в таком случае достаточно снова выполнить `/anime ...`.

## Rich-карточка аниме

Основная карточка отправляется через `sendRichMessage`.

Пример структуры:

```text
[обложка]

О моём перерождении в слизь

Тип: TV
Статус: вышло
Серии: 24/24
Оценка Shikimori: ...
Студии: ...
...

Подробная информация

Описание — нажмите, чтобы открыть
Все названия — нажмите, чтобы открыть
Авторы и команда — нажмите, чтобы открыть
Сэйю — нажмите, чтобы открыть
```

Названия разделов — это `tg-button` с `style="link"`, встроенные прямо в текст rich message.

При нажатии бот получает callback и заменяет содержимое той же карточки через редактирование rich message.

### Навигация внутри раздела

В подробных разделах снизу остаются обычные inline-кнопки:

```text
[ ← Назад ]
```

Если раздел длиннее допустимого размера одного rich message:

```text
[ ← Назад ]
[ ◀️ ] [ 1/2 ] [ ▶️ ]
```

Это особенно полезно для длинных списков команды или сэйю.

## Обложки Shikimori

Для постера запрашиваются сразу несколько вариантов качества:

```text
originalUrl
main2xUrl
mainUrl
preview2xUrl
previewUrl
```

Бот выбирает лучший доступный вариант в этом порядке.

В текущей GraphQL-схеме Shikimori `poster` представляет один постер аниме, а перечисленные URL — разные производные размеры/варианты этого изображения. Бот не показывает один и тот же постер несколько раз только потому, что API вернул несколько размеров.

Функция `poster_urls()` сделана так, чтобы работать и со списком постеров, если источник в будущем начнёт отдавать несколько отдельных изображений. В таком случае несколько обложек можно отобразить внутри rich message как slideshow.

## Какие данные сейчас берутся из Shikimori

Карточка может содержать:

- Shikimori ID;
- MyAnimeList ID;
- русское название;
- romaji / основное название;
- английское название;
- японское название;
- лицензионное русское название;
- синонимы;
- тип аниме;
- статус;
- количество серий;
- количество вышедших серий;
- длительность серии;
- рейтинг;
- оценку Shikimori;
- сезон;
- франшизу;
- дату начала показа;
- дату окончания;
- время следующего эпизода, если оно доступно;
- жанры;
- студии;
- лицензиатов;
- описание;
- авторов и производственную команду;
- сэйю;
- ссылку на страницу Shikimori;
- постер.

## Telegram API режимы

Бот имеет два отдельных entry point, но общую логику:

```text
bots/official.py
bots/tgapi.py
```

### Официальный Bot API

В `.env`:

```env
TELEGRAM_BOT_API_URL=
```

Будет запущен:

```bash
python -m bots.official
```

Запросы идут через:

```text
https://api.telegram.org
```

### Собственный telegram-bot-api

Пример:

```env
TELEGRAM_BOT_API_URL=http://127.0.0.1:8081
TELEGRAM_BOT_API_LOCAL=true
```

Будет запущен:

```bash
python -m bots.tgapi
```

`TELEGRAM_BOT_API_LOCAL=true` нужно устанавливать только если сам процесс `telegram-bot-api` работает с флагом `--local`.

В обоих режимах бот использует rich messages. Отличается только endpoint, через который идут запросы Telegram API.

## Конфигурация `.env`

Скопируй пример:

```bash
cp .env.example .env
```

Минимальный вариант:

```env
BOT_TOKEN=123456:YOUR_BOT_TOKEN

TELEGRAM_BOT_API_URL=
TELEGRAM_BOT_API_LOCAL=false

SHIKIMORI_API_URL=https://shikimori.io/api/graphql
SHIKIMORI_SITE_URL=https://shikimori.io
```

### Переменные

| Переменная | Назначение |
| --- | --- |
| `BOT_TOKEN` | токен Telegram-бота из BotFather |
| `TELEGRAM_BOT_API_URL` | URL собственного Bot API; пустое значение включает официальный API |
| `TELEGRAM_BOT_API_LOCAL` | `true`, если self-hosted Bot API запущен с `--local` |
| `SHIKIMORI_API_URL` | GraphQL endpoint Shikimori |
| `SHIKIMORI_SITE_URL` | базовый URL сайта для формирования ссылок |

`.env` не должен попадать в Git.

## Установка и запуск на Ubuntu / Debian

Понадобятся:

- Python 3.11+;
- `python3-venv`;
- `pip`;
- `tmux`;
- Git.

Установка системных пакетов:

```bash
sudo apt update
sudo apt install git python3 python3-venv python3-pip tmux
```

Клонирование:

```bash
git clone git@github.com:Winbil/anime-db-bot.git
cd anime-db-bot
```

Конфигурация:

```bash
cp .env.example .env
nano .env
```

Запуск:

```bash
./start.sh
```

## Что делает `start.sh`

Скрипт:

1. проверяет наличие `python3` и `tmux`;
2. проверяет структуру проекта;
3. создаёт `.venv`, если его ещё нет;
4. восстанавливает `pip`, если venv был создан некорректно;
5. устанавливает зависимости из `requirements.txt`;
6. выполняет `pip check`;
7. проверяет нужные Python imports;
8. создаёт `.env` из `.env.example`, если файла ещё нет;
9. проверяет `BOT_TOKEN`;
10. выбирает `bots.official` или `bots.tgapi` по `TELEGRAM_BOT_API_URL`;
11. запускает бота в tmux-сессии `anime-db-bot`;
12. пишет вывод в `logs/bot.log`.

## Повторный запуск

Если бот уже работает и снова выполнить:

```bash
./start.sh
```

скрипт спросит:

```text

```

Поддерживаются ответы:

```text
y
yes
д
да
```

Любой другой ответ оставит текущий экземпляр работающим.

## Как добавить новый источник

Рекомендуемая схема:

1. создать отдельный файл в `sources/`, например:

```text
sources/anilist.py
```

2. держать внутри него только код конкретного API:

- endpoint;
- запросы;
- авторизацию;
- преобразование ответа;
- функции получения данных;
- source-specific обработку ошибок.

3. не добавлять сетевые запросы нового сервиса напрямую в `bots/common.py`;
4. Telegram-слой должен только вызывать функции модулей источников и объединять готовые данные.

Так проект останется пригодным для отключения и замены отдельных баз.

## Планируемые источники

### AniList

Планируется использовать для:

- расписания выхода серий;
- дополнительных ID;
- альтернативных метаданных.

### AniDB

Планируется использовать для более глубокой технической информации об аниме и связях между сущностями.

### AnimeThemes

Планируется использовать для:

- opening;
- ending;
- исполнителей;
- связанных видео/тем.

### SkipDB

Планируется использовать для временных сегментов эпизодов:

- opening;
- ending;
- recap;
- preview;
- другие пропускаемые участки.

## Fallback-поведение

Если `sendRichMessage` или редактирование rich message не удалось, бот пытается перейти на обычный `sendMessage` / `editMessageText`.

В fallback-режиме часть rich-возможностей, например встроенное изображение или callback-текст внутри сообщения, может быть недоступна. В таком случае используются обычные inline-кнопки.

## Известные особенности

- поисковая пагинация хранит исходный запрос в памяти процесса; после перезапуска старые кнопки поиска могут перестать работать;
- данные зависят от полноты информации в используемых внешних базах;
- Shikimori может не иметь заполненного описания, студии, роли или альтернативного названия для конкретного тайтла;
- один очень длинный раздел может быть разбит на несколько rich-страниц;
- количество источников пока ограничено Shikimori, но структура уже рассчитана на дальнейшее расширение.
